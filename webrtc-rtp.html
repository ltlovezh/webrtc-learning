RTP · REAL-TIME TRANSPORT PROTOCOLRTP 封装：一帧视频怎么变成一串包

编码器吐出来的是一条连续的 H.264 / H.265 码流；网络上跑的却是一个个不超过 1200 字节、可能丢、可能乱序的 UDP 包。RTP 就是两者之间的那层「打包规矩」。

这一页只做一件事：看清一帧画面怎样被切开、装箱、编号，又怎样在对面被一字节不差地拼回去。RTCP 另起一篇。

RFC 3550 · RTPRFC 6184 · H.264 over RTPRFC 7798 · H.265 over RTP
一 · 先分清两兄弟

RTP 运货，RTCP 打电话

RTP 和 RTCP 总是成对出现，但干的是两种活。RTP 只管把媒体本身送过去：每个包都带着序号、时间戳和「我是哪一路流」，接收端据此排队、发现丢包、按时播放。RTCP 不运媒体，只汇报和喊话：发送端定期说「我发了多少、我的时钟是几点」，接收端回话「丢了多少、抖得多厉害、第几号包重发一下、给我一个关键帧」。

两条车道粗管是 RTP，一刻不停；细线是 RTCP，定期往返、出事时立刻喊

一句话记住：RTP 是货车，RTCP 是调度电话。货车没有电话也能跑，但跑得好不好、哪里出了事，全靠电话里那几句话。这一页先把货车拆开看，电话的内容留到下一篇。

二 · 拆开一个 RTP 包

一个包，七层包装

先看全貌。下面是一个真实形状的视频包：一帧关键帧（IDR）被切开后的第一片。从下往上就是字节在线路上的顺序——最外层的 IP、UDP 是网络的事，中间的 RTP 头是本页主角，最上面才是视频数据本身。拖动可以旋转，点「合拢」看它在线路上其实是一整块。

拖动旋转 · 方向键也可以

    斜纹的两层（FU-A 头与 NAL 分片）在 SRTP 里是加密的；RTP 头和扩展默认是明文——SFU 要读序号和 SSRC 才能转发。示例：RTP 头 + 扩展 + 载荷 = 1200 字节，正是 libwebrtc 的默认上限 kVideoMtu；再加上 SRTP 标签和 UDP/IP 头约 1238 字节，仍低于以太网的 1500 字节，不会被 IP 分片。

    RTP 头逐位拆开

    RTP 固定头只有 12 个字节，后面按需跟着头扩展，再往后就是载荷。下面每一格都能点，下方的十六进制会同步亮起对应的字节。图里每行 32 位，也就是 4 个字节。

    序号和时间戳：两把不同的尺子

    新手最容易混的两个字段。序号按「包」数，每包加 1，用来发现丢包和乱序；时间戳按「采样时刻」数，同一帧的所有包都相同，用来决定什么时候播放。点任意一个包把它「弄丢」，看接收端怎么发现。

    帧率
    视频时钟 90 kHz · 每帧时间戳 +3000

    两把尺子的起点都是随机的（RFC 3550 这样要求，让加密更难被猜）。音频也一样，只是时钟不同：Opus 按 48 kHz 计，20 ms 一包，每包时间戳 +960。

    三 · 先认识要装的货

    H.264 / H.265 码流：一串 NAL 单元

    编码器输出的码流（叫 Annex B 格式）是一长串 NAL 单元，每个 NAL 前面垫着一个起始码 00 00 00 01，解码器靠它找到边界。一帧关键帧通常是：参数集（SPS、PPS，H.265 还多一个 VPS）+ 一个很大的 IDR 片；普通帧往往只有一个片。

    一帧 H.264 关键帧的码流灰色是起始码，后面紧跟 NAL 头字节
    00 00 00 0167 …SPS · 16B 00 00 00 0168 …PPS · 6B 00 00 00 0165 88 84 00 33 …IDR 片 · 4200B

    起始码会和数据撞车吗？——防竞争字节

    如果片数据里恰好出现 00 00 01，解码器会误以为新 NAL 开始了。所以编码器写码流时，凡是连续两个 00 后面跟着 00～03，就插一个 03 进去：

    原始…000001…写进码流…00000301…

    这个 03 属于 NAL 的一部分。打包和解包时都原样保留，只有解码器在解析时才把它去掉。

    关键一点：RTP 里不需要起始码。包的边界、聚合包里的长度字段已经能分隔 NAL，所以发送端打包前把起始码去掉，接收端解包后再加回来。

    NAL 头：第一个字节（H.265 是前两个）决定一切

    每个 NAL 开头的头字节说明「我是什么」。点下面的例子看每一位的意思。注意最后两个：它们不是编码器产生的，只在 RTP 包里出现，是打包时借用的「类型号」。

    四 · 装箱

    封装：三种装法，按 NAL 大小挑

    一个 RTP 包装多少，看 NAL 有多大。规则只有三条，H.264 和 H.265 思路完全相同，只是类型号和头的长度不同。

    刚好装得下

    单 NAL 包

    一个 NAL 原样放进一个包，NAL 头就是载荷的第一个字节。普通帧的小片常这样走。

    太小 · 拼车

    聚合包 STAP-A / AP

    几个小 NAL 合坐一个包：一个聚合头，然后每个 NAL 前面加 2 字节长度。关键帧的 SPS、PPS 通常这样走。

    太大 · 切开

    分片包 FU-A / FU

    一个大 NAL 切成几段，每段前面加分片头，标明「开始 / 中间 / 结束」。原 NAL 头不单独发送，藏在分片头里。

    封装模拟器调参数，看一帧怎么被装进 RTP 包；点任意一个包看它的头

    RTP 包（宽度 = 占用了包上限的多少）

    切片时 libwebrtc 会让各段大小尽量相等（SplitAboutEqually），而不是前面塞满、最后剩一点。模拟器里的包上限包含 12 字节 RTP 固定头，没算头扩展。

    解封装：把包拼回解码器认识的码流

    接收端拿到的是上面模拟器发出的那串包——但网络会打乱顺序，偶尔还会丢一个。下面一步步走一遍接收端要做的事。改上面的参数，这里会跟着变。

    六 · 解封装的坑

    拼回去之前，这几件事必须做对

    帧边界

    一帧在哪里结束？

    同一帧的包时间戳相同；Marker 位为 1 的包是这一帧的最后一片。时间戳一变，就是新的一帧开始了。libwebrtc 的 PacketBuffer 就靠这两条判断一帧是否收齐。

    丢片

    少一片，整个 NAL 作废

    分片之间是连续的字节流，缺了中间一段，后面的数据就对不上了，不能「只解前半截」。接收端先用 NACK 请求重传；等不到就发 PLI 请求关键帧，从头再来。

    参数集

    SPS / PPS 必须先到

    没有参数集，IDR 片解不了。它们要么在关键帧前带内发送（通常聚合在一个包里），要么写在 SDP 的 sprop-parameter-sets（H.265 是 sprop-vps / sps / pps）。libwebrtc 用 H264SpsPpsTracker 在关键帧前补齐。

    防竞争字节

    不要「顺手」删掉 03

    NAL 里的 00 00 03 是码流的一部分，打包、解包都原样保留，交给解码器处理。删了会让解码器读错位。

    打包模式

    packetization-mode=0 不能分片

    H.264 模式 0 只允许单 NAL 包，大 NAL 无处可去，编码器必须把画面切成多个小片。WebRTC 一般协商模式 1（单 NAL + STAP-A + FU-A）；模式 2（交错）WebRTC 不用。

    H.265 专属

    DONL 字段：WebRTC 里没有

    RFC 7798 规定，当 SDP 里 sprop-max-don-diff 大于 0 时，AP 和 FU 里会多出 2 字节的解码顺序号（DONL）。WebRTC 不用这个特性，所以本页的包里都没有它。

一 · 先分清两兄弟

RTP 运货，RTCP 打电话

RTP 和 RTCP 总是成对出现，但干的是两种活。RTP 只管把媒体本身送过去：每个包都带着序号、时间戳和「我是哪一路流」，接收端据此排队、发现丢包、按时播放。RTCP 不运媒体，只汇报和喊话：发送端定期说「我发了多少、我的时钟是几点」，接收端回话「丢了多少、抖得多厉害、第几号包重发一下、给我一个关键帧」。

两条车道粗管是 RTP，一刻不停；细线是 RTCP，定期往返、出事时立刻喊

一句话记住：RTP 是货车，RTCP 是调度电话。货车没有电话也能跑，但跑得好不好、哪里出了事，全靠电话里那几句话。前七节先把货车拆开看，第八节起再拆电话。

二 · 拆开一个 RTP 包

一个包，七层包装

先看全貌。下面是一个真实形状的视频包：一帧关键帧（IDR）被切开后的第一片。从下往上就是字节在线路上的顺序——最外层的 IP、UDP 是网络的事，中间的 RTP 头是本页主角，最上面才是视频数据本身。拖动可以旋转，点「合拢」看它在线路上其实是一整块。

拖动旋转 · 方向键也可以

    斜纹的两层（FU-A 头与 NAL 分片）在 SRTP 里是加密的；SRTP 只加密载荷，RTP 头和头扩展默认不加密，序号、SSRC 在线路上都看得见。（加密是逐跳的：SFU 本身就是 DTLS 连接的另一端，载荷它也能解开。）示例：RTP 头 + 扩展 + 载荷 = 1200 字节，正是 libwebrtc 的默认上限 kVideoMtu；再加上 SRTP 标签和 UDP/IP 头约 1238 字节，仍低于以太网的 1500 字节，不会被 IP 分片。

    RTP 头逐位拆开

    RTP 固定头只有 12 个字节，后面按需跟着头扩展，再往后就是载荷。下面每一格都能点，下方的十六进制会同步亮起对应的字节。图里每行 32 位，也就是 4 个字节。

    序号和时间戳：两把不同的尺子

    新手最容易混的两个字段。序号按「包」数，每包加 1，用来发现丢包和乱序；时间戳按「采样时刻」数，同一帧的所有包都相同，用来决定什么时候播放。点任意一个包把它「弄丢」，看接收端怎么发现。

    帧率
    视频时钟 90 kHz · 每帧时间戳 +3000

    两把尺子的起点都是随机的：libwebrtc 的序号起点在 1～32767 里随机取，源码注释说避开上半段是为了防止 SRTP 刚启动就回绕出错（packet_sequencer.cc）；时间戳偏移也是一个随机数（rtp_sender.cc）。音频同理，只是时钟不同：libwebrtc 的 Opus 时钟固定 48 kHz，默认 20 ms 一包（kOpusDefaultPTime），所以每包时间戳 +960。

    三 · 先认识要装的货

    H.264 / H.265 码流：一串 NAL 单元

    编码器输出的码流（叫 Annex B 格式）是一长串 NAL 单元，每个 NAL 前面垫着一个起始码 00 00 00 01，解码器靠它找到边界。一帧关键帧通常是：参数集（SPS、PPS，H.265 还多一个 VPS）+ 一个很大的 IDR 片；普通帧往往只有一个片。

    一帧 H.264 关键帧的码流灰色是起始码，后面紧跟 NAL 头字节
    00 00 00 0167 …SPS · 16B 00 00 00 0168 …PPS · 6B 00 00 00 0165 88 84 00 33 …IDR 片 · 4200B

    起始码会和数据撞车吗？——防竞争字节

    如果片数据里恰好出现 00 00 01，解码器会误以为新 NAL 开始了。所以编码器写码流时，凡是连续两个 00 后面跟着 00～03，就插一个 03 进去：

    原始…000001…写进码流…00000301…

    这个 03 属于 NAL 的一部分。打包和解包时都原样保留，只有解码器在解析时才把它去掉。

    关键一点：RTP 里不需要起始码。包的边界、聚合包里的长度字段已经能分隔 NAL，所以发送端打包前把起始码去掉，接收端解包后再加回来。

    NAL 头：第一个字节（H.265 是前两个）决定一切

    每个 NAL 开头的头字节说明「我是什么」。点下面的例子看每一位的意思。注意最后两个：它们不是编码器产生的，只在 RTP 包里出现，是打包时借用的「类型号」。

    四 · 装箱

    封装：三种装法，按 NAL 大小挑

    一个 RTP 包装多少，看 NAL 有多大。规则只有三条，H.264 和 H.265 思路完全相同，只是类型号和头的长度不同。

    刚好装得下

    单 NAL 包

    一个 NAL 原样放进一个包，NAL 头就是载荷的第一个字节。普通帧的小片常这样走。

    太小 · 拼车

    聚合包 STAP-A / AP

    几个小 NAL 合坐一个包：一个聚合头，然后每个 NAL 前面加 2 字节长度。关键帧的 SPS、PPS 通常这样走。

    太大 · 切开

    分片包 FU-A / FU

    一个大 NAL 切成几段，每段前面加分片头，标明「开始 / 中间 / 结束」。原 NAL 头不单独发送，藏在分片头里。

    六 · 解封装的坑

    拼回去之前，这几件事必须做对

    帧边界

    一帧从哪开始、到哪结束？

    Marker 位为 1 的包是一帧的最后一个包。H.264 包里没有可靠的「帧开始」标志，libwebrtc 就从 Marker 包往回找：序号连续、时间戳相同的都算这一帧，直到遇上时间戳不同的包或空缺（PacketBuffer::FindFrames，源码注释引用 webrtc:7106；H.265 走的 H26xPacketBuffer 也是同样的找法）。

    丢包

    少一个包，整帧都出不去

    包缓冲区只交出序号连续、首尾齐全的帧，缺一个包，这一帧就一直留在缓冲区里。接收端发 NACK 请求重传（NackRequester）；如果迟迟没有可解码的帧——等关键帧时 200 ms、平时 3 s（kMaxWaitForKeyFrame / kMaxWaitForFrame）——就请求关键帧。

    参数集

    SPS / PPS 必须先到

    没有参数集，IDR 片解不了。libwebrtc 自己生成的 SDP 不带 sprop 参数（RFC 7742 不允许），所以参数集基本靠带内发送。H.264 收到对端 SDP 里的 sprop-parameter-sets 时会存进 H264SpsPpsTracker，在 IDR 前补上；IDR 到了却找不到对应的 SPS / PPS，就直接请求关键帧。H.265 的 sprop 参数 libwebrtc 不处理（media_constants.h 注释）。

    防竞争字节

    不要「顺手」删掉 03

    NAL 里的 00 00 03 是码流的一部分，打包、解包都原样保留，交给解码器处理。删了会让解码器读错位。

    打包模式

    packetization-mode=0 不能分片

    H.264 模式 0 只允许单 NAL 包，大 NAL 无处可去，libwebrtc 会直接报错打包失败，编码器必须把画面切成多个小片。libwebrtc 只实现了模式 0 和模式 1（H264PacketizationMode 只有 SingleNalUnit、NonInterleaved 两个值），模式 2（交错）不支持。

    H.265 专属

    DONL 字段：WebRTC 里没有

    RFC 7798 规定，当 SDP 里 sprop-max-don-diff 大于 0 时，AP 和 FU 里会多出 2 字节的解码顺序号（DONL）。libwebrtc 的 H.265 打包器在单 NAL、AP、FU 三处都注明不支持 DONL，所以本页的包里都没有它；PACI 包的解析也还没实现（源码里是 TODO）。

    libwebrtc 生成 offer 时默认带 a=rtcp-rsize（media_session.cc），answer 跟随 offer；协商成功就用精简模式：报告按周期发，NACK、PLI 这类急事可以只发一个小包。复合模式还有个约束：自己是发送方、却还没发出过任何媒体时，算不出 SR 里的 RTP 时间戳，这时连 SR 带其他 RTCP 都发不出去（RTCPSender 的注释：Not allowed to send any RTCP packet without sender report）。

    九 · 定期报平安

    SR 与 RR：一份报告里写了什么

    正在发媒体的一端发 SR，只收不发的一端发 RR（RTCPSender::PrepareReport：sending_ ? kRtcpSr : kRtcpRr）。SR 比 RR 多一段「发送者信息」；两者后面都可以挂若干个 24 字节的报告块，每块汇报自己收到的一路流。下面是一份带 1 个报告块的 SR，共 52 字节，每一格都能点。

    RTT：两端的钟不用对准也能算

    A 发出 SR，B 记下「收到的那份 SR 的时间」作为 LSR，过一会儿在报告块里写上 LSR 和「我压了多久才回」（DLSR）。A 收到后用自己的钟算：RTT = 收到时刻 − DLSR − LSR。B 的钟只用来量一段时长，所以两边的时钟不需要同步。这就是 RTCPReceiver 里的那一行：rtt_ntp = receive_time_ntp - delay_ntp - send_time_ntp。

    时间都用「压缩 NTP」表示：取 64 位 NTP 时间的中间 32 位，单位是 1/65536 秒。LSR 为 0 表示 B 还没收到过 SR，libwebrtc 这时不算 RTT。只收不发的一端发不了 SR，就用 RTCP XR 里的 RRTR / DLRR 做同样的计算（GetAndResetXrRrRtt）。

    抖动：时间戳间隔和到达间隔差了多少

    报告块里的「到达间隔抖动」不是一次测量，而是一个平滑过的估计。libwebrtc 每收到一个包就算一次：D = 到达间隔（换算成 RTP 刻度）− 时间戳间隔，再用 J += (|D| − J) / 16 慢慢逼近（receive_statistics_impl.cc，用 Q4 定点数避免浮点）。拖动滑块看网络越抖，J 怎么跟着变。

    十 · 音画同步

    SR 里那一对时间戳，是嘴型对上声音的关键

    音频和视频是两路独立的 RTP 流：SSRC 不同、时钟不同（Opus 48 kHz，视频 90 kHz）、起点都是随机数。只看 RTP 时间戳，根本不知道哪个声音包和哪一帧画面是同一时刻采的。SR 里那一对「NTP 墙上时钟 + RTP 时间戳」，就是把各自的 RTP 时间戳换算到同一块表上的换算表。

    接收端手里有

    libwebrtc 的做法分两步。换算：每路流用最近最多 20 份 SR 的（RTP, NTP）对做线性回归（RtpToNtpEstimator，kNumRtcpReportsToUse = 20）。对齐：StreamSynchronization 算出两路的相对延迟 =（视频到达时间 − 音频到达时间）−（视频采集时间 − 音频采集时间），先做平滑（每次新值只占 1/4，kFilterLength = 4）；差距不到 30 ms 就不动，否则每次只调差值的一半、最多 80 ms，一点点拉齐。哪路音频和哪路视频算一组，看 SDP 里 msid 的流 ID（sync_group）。

    十一 · 出事时立刻喊

    反馈：NACK、PLI、FIR、transport-cc

    报告是定期的，反馈是即时的（RFC 4585）。能不能用某种反馈，要在 SDP 里用 a=rtcp-fb 协商。libwebrtc 给每个视频编码默认加上这五行（AddDefaultFeedbackParams，media/base/codec.cc）：

a=rtcp-fb:96 ccm fir
a=rtcp-fb:96 nack
a=rtcp-fb:96 nack pli

a=fmtp:97 apt=96
a=ssrc-group:FID 1A2B3C4D 5C6D7E8F

    载荷类型和 SSRC 都换成 RTX 的，头扩展照抄，载荷前面加 2 字节原序号（OSN）（kRtxHeaderSize = 2）。重传流有自己的 SSRC 和序号空间；SDP 里 apt=96 说明它是谁的重传流，FID 分组把两个 SSRC 绑在一起。simulcast 时，RTX 包用 RRID（RepairedRtpStreamId）扩展而不是 RID 标明自己修补的是哪一层（源码注释）。

    等重传，还是要关键帧？

    libwebrtc 里没有「超过多少毫秒就放弃重传」这一个开关，而是几条规则叠在一起（nack_requester.cc、video_receive_stream2.cc）。调一调 RTT 和「重传包又丢了几次」，看这一帧最后靠什么救回来。

    规则源码里的常量结果
    NACK 过一个 RTT 没回音就再发rtt_（默认 100 ms）同一个包最多 NACK 100 次（kMaxNackRetries）
    太老的包不再追kMaxPacketAge = 10000比最新序号落后 1 万以上的从 NACK 列表删掉
    缺得太多kMaxNackPackets = 1000清空 NACK 列表，直接请求关键帧
    迟迟没有可解码的帧kMaxWaitForFrame = 3 s / kMaxWaitForKeyFrame = 200 ms请求关键帧（等关键帧期间用 200 ms）
    H.264 的 IDR 缺参数集H264SpsPpsTracker立即请求关键帧

    transport-cc 回报的到达时间，最终喂给发送端的拥塞控制（GCC）去估带宽——那是「拥塞控制与带宽估计」专题的内容。

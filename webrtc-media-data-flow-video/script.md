# WebRTC 媒体数据传输教学视频旁白

上一集我们讲了 WebRTC 呼叫建立时，Offer、Answer、Candidate 是怎么交换的。那连接建立以后，真正的音视频数据是怎么流动的？这一集我们只抓住四个最常见的形态：P2P 直连、TURN 中继、SFU 转发，以及 MCU 合流加 CDN 分发。

WebRTC 里的音视频不是直接把一整段视频文件发过去。浏览器会先采集麦克风和摄像头，经过编码后切成一个个 RTP 包。真正上网传输时，这些 RTP 包会被 SRTP 加密。与此同时，RTCP 会持续反馈网络质量，比如丢包、延迟、码率估计和关键帧请求。所以可以先记住：RTP 承载媒体，SRTP 负责加密，RTCP 负责质量反馈。

一对一通话里，WebRTC 会优先尝试 P2P 直连。也就是说，音视频媒体包直接在用户 A 和用户 B 之间传输，业务服务器不转发真正的音视频数据。这个形态延迟低，链路短，成本也低。前提是 ICE 能找到一条可用的直连路径，比如局域网路径，或者 NAT 穿透成功后的公网映射路径。

但现实网络不总是这么理想。用户可能在复杂 NAT、公司防火墙或者运营商网络后面，直连可能失败。这时 WebRTC 会使用 TURN 中继。TURN 的职责很克制：它只转发加密后的 SRTP 和 RTCP 包，不解码音视频，不理解画面内容，也不做混流。它解决的是“网络能不能连上”的问题，而不是“多人媒体怎么组织”的问题。

当进入多人连麦互动，主流架构通常是 SFU。每个连麦用户只把自己的一路音视频上传到 SFU，其他人再按需从 SFU 拉取需要看的流。它通常不把所有画面混成一张图，而是维护订阅关系，选择性转发多路 RTP 流。比如主播需要看到所有嘉宾，嘉宾可能只需要看到主播和当前发言人，上麦观众可能只需要低清画面或音频。为了适配不同网络和设备，发送端可以用 Simulcast 同时上传多档清晰度，也可以用 SVC 在同一路码流里分出可选择的层。SFU 再结合 RTCP 反馈，根据丢包、带宽估计和设备能力，动态决定给每个接收端转发哪一层。它的核心价值是：让多人互动保持低延迟，同时避免每个人都给所有人单独上传一份媒体流。

直播间里还有另一类用户：普通看播用户。他们只看，不上麦，也不需要和每个嘉宾单独建立实时互动连接。这个时候，系统常常会把连麦房间的多路音视频送到 MCU 或合流服务。MCU 会解码多路音频和视频，完成混音、拼画面、重新编码，生成一条适合大众观看的节目流。然后这条流再进入传统 CDN，分发给大量普通观众。这样，连麦区仍然可以低延迟互动，而看播区可以用更适合大规模分发的直播链路。

总结一下：P2P 是一对一优先使用的直连路径；TURN 是直连失败时的网络兜底；SFU 负责多人连麦里的低延迟选择性转发；MCU 负责把多路连麦内容加工成一路节目流，再交给 CDN 分发给普通观众。入门阶段不用一次记住所有复杂拓扑，只要先抓住这条主线：一对一看路径，多人互动看 SFU，大规模看播看 MCU 合流和 CDN 分发。

最后快速对一下视频里出现的缩写和概念。P2P 是 Peer to Peer，点对点，用于两端直接传输媒体。TURN 是 Traversal Using Relays around NAT，通过中继穿越 NAT，用于直连失败时转发加密媒体包。SFU 是 Selective Forwarding Unit，选择性转发单元，用于多人互动中按需转发 RTP 流。Simulcast 是同步多码流发送，用于同时提供多档清晰度。SVC 是 Scalable Video Coding，可伸缩视频编码，用于在同一路码流里提供可选择的层。MCU 是 Multipoint Control Unit，多点控制单元，用于解码、混音、拼画面和重新编码。CDN 是 Content Delivery Network，内容分发网络，用于把合流后的直播流分发给大量观众。RTP 是 Real-time Transport Protocol，实时传输协议，用于承载音视频媒体包。SRTP 是 Secure Real-time Transport Protocol，安全实时传输协议，用于加密传输 RTP。RTCP 是 RTP Control Protocol，RTP 控制协议，用于反馈丢包、延迟、码率和关键帧请求。NAT 是 Network Address Translation，网络地址转换，会影响端到端连通性。ICE 是 Interactive Connectivity Establishment，交互式连接建立，用于寻找可用网络路径。
